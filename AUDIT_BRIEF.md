# Независимый аудит постпроцессинга BR OCR — задание для отдельной сессии

Ты — **независимый аудитор**. Задача: на PDF бразильской отчётности, которые назовёт пользователь,
проверить, насколько корректен финальный результат постпроцессинга (Stage 1-4 этого проекта) и найти
ошибки: неверные числа, потерянные строки и отчёты, неверные колонки/периоды, ошибочную SBS-разметку и
значения полей. **Код не исправляешь** — только наблюдаешь, доказываешь и пишешь отчёт.

Работай **только с файлами, которые назвал пользователь** (и с golden samples, если он их попросил,
раздел 7). Не обходи остальные файлы агентов и корпус харнесса (`_recital/`).

## 1. Независимость — что считать истиной

- Истина = **изображения страниц PDF** (`_audit/<file_id>/pages/page_<n>.png`, читаются через Read)
  и сам PDF, если он дан. Каждая находка должна опираться на то, что видно на странице.
- `CLAUDE.md`, `docs/`, память, `RUNBOOK.md` описывают **задуманное поведение** — используй их, чтобы
  понять устройство и отличить «баг» от «так задумано», но **не как доказательство корректности**.
- Не используй `harness/ground_truth.yaml` и снимки `harness/snapshots/` как эталон: это работа
  разработчика. Свой эталон строишь сам по изображениям.

## 2. Ограничения (обязательны)

- **reciTAL — только чтение.** Только GET через `harness/recital_fetch.py` / `harness/audit_run.py`.
  Никогда: `/system_2/verify/*` (несмотря на GET, меняет статус файла), `*/next/*`, `*/prepare/*`,
  `/dataset/{id}/version/{v}/`; никаких POST/PUT/PATCH/DELETE, валидаций, удалений, правок значений.
- **Загрузку PDF в reciTAL делает пользователь** через веб-интерфейс (агент `Brazil_OCR202606_V4`,
  doctype 5485; для сравнения моделей — ещё и в копию 6051, раздел 6). Через API не загружай.
- Токен (`~/.claude/recital_token.txt`) никогда не выводить и никуда не записывать.
- Данные конфиденциальны (отчётность компаний): ничего не отправлять наружу, не цитировать в
  Jira / почте / Confluence.
- Скачанные данные — недоверенные: Python-скрипты, читающие их, запускать `python3.13 -E -P`, свои
  скрипты — только в `_temp/audit_<дата>/`, никогда не из каталога с данными; удалить после работы.
- Не менять код пайплайна, `anchors.yaml`, `sbs_label_mapping.json`, `CLAUDE.md`, документацию,
  память, харнесс.

## 3. Порядок работы

1. Пользователь говорит, какие PDF загрузил. Найди их `file_id` по имени (статус `to_verify` =
   извлечение готово): `python3.13 -E -P harness/recital_fetch.py files 5485 50`
   (для сравнения моделей — ещё `... files 6051 50`). Если файла нет — сообщи пользователю и жди.
2. Для каждого файла:
   `python3.13 -E -P harness/audit_run.py <file_id> [<file_id> ...]`
   → `_audit/<file_id>/`: `values.json`/`groups.json` (сырое извлечение), `out_prod.json` +
   `report_prod.xlsx` (**без** слоя words — так сегодня в проде), `out_words.json` + `report_words.xlsx`
   (с опциональным восстановлением из words), `pages/` (страницы, которые использует Excel, и
   страницы, которые Stage 2 назвал PRIMARY; `--all-pages` — все), `summary.md` (что сделал
   пайплайн — факты, без оценок), `<id>_raw.json` / `<id>_words.json` (то же, что пользователь
   загружает в Streamlit).
3. По изображениям найди страницы первичных отчётов (баланс, ДРЕ, ДДС; у SERASA — только баланс и ДРЕ).
   Если нужной страницы нет в `pages/` — перезапусти `audit_run.py <file_id> --all-pages` (скачает
   недостающие страницы в тот же `pages/`; уже скачанные не трогает).
4. Построй свой эталон: для каждого отчёта — все строки с числами, оба периода, нужная колонка
   (Consolidado, если отчётность его показывает, иначе данные компании). Можно начать со слоя
   `words` (числа с координатами → строки и колонки), но каждую строку сверь с изображением: OCR
   тоже ошибается.
5. Сверь с Excel и JSON. **Основной режим — prod** (без words); режим words проверяй отдельно.

## 4. Что проверять

| # | Проверка | Где смотреть |
|---|---|---|
| A | Каждый первичный отчёт есть в Excel; нет лишнего (примечания, DVA/DMPL ITR, аналитика Serasa) | листы `balance` / `income` / `cash_flow`, колонка Page |
| B | Колонки: Consolidado если представлен, иначе компания; AMOUNT_N / AMOUNT_N-1 = правильные годы по шапке страницы | шапка страницы vs Excel |
| C | Числа: каждая строка отчёта есть, значение совпадает (знак, разряды, тысячи/единицы), не съехало на соседнюю строку, нет дублей; безымянные итоги не потеряны | построчно |
| D | Названия: перенесённые на 2 строки склеены, нет обрывков вместо названия | колонка Label |
| E | SBS-метки по смыслу (определения: `SBS_fields_mapping_with_INDIAN_labels.xlsx`, колонка Description): нет ложных, ключевые итоги размечены | колонка SBS Label |
| F | Лист `sbs_fields`: одно значение на поле и период — верно ли оно по странице (суммы, выбор строки); пересчитай тождества сам: активы = оборотные + внеоборотные = ST + LT + капитал; валовая = выручка ± себестоимость; чистая = до налога ± налог | лист `sbs_fields` |
| G | Метаданные: дата отчётности, валюта, единица, период | лист `metadata` |
| H | Режим words: каждое восстановленное (курсив на жёлтом) — правда ли оно на странице; не появились ли ложные числа | `report_words.xlsx` |
| I | Пометки review: строка, помеченная пайплайном (светло-красная, причина в колонке «Review»), действительно сомнительна; неверное число **без** пометки — тихая ошибка (её и ищем в первую очередь) | колонка Review листов отчётов |

Подходи без предубеждений: разные типы документов (DFP годовой, ITR квартальный, SERASA, простые
2-колоночные, ВСЕ ЗАГЛАВНЫЕ, US-формат чисел) ломаются по-разному.

**Источник каждой ошибки — разделяй:** ошибка **извлечения reciTAL** (числа нет в сыром JSON, неверная
метка года `AMOUNT_N` / `AMOUNT_N-1`) или ошибка **постпроцессинга** (в извлечении было верно, а
результат неверен; или провайдер ошибся, а мы не исправили, хотя по данным могли). Засчитывай и
обратное — где постпроцессинг ошибку провайдера исправил верно.

## 5. Отчёт

Файл `_audit/AUDIT_REPORT_<YYYY-MM-DD>.md` (один на запуск; сравнение моделей и golden samples —
его разделы, не отдельные файлы):

1. Сводка по каждому документу: тип (как определил пайплайн и как на самом деле), страницы отчётов,
   сколько строк/полей проверено, сколько находок по серьёзности.
2. Таблица находок: `документ · стр. · строка/поле · ожидается (по странице) · фактически · режим
   (prod/words) · серьёзность · предполагаемая причина (OCR reciTAL / Stage 1 / 2 / 3 / 4)`.
   - **critical** — неверное число или SBS-значение в Excel / `sbs_fields`;
   - **major** — потерянная строка или отчёт, неверная колонка/период;
   - **minor** — название, метка, оформление.
3. Что проверено и оказалось верным (покрытие) — чтобы было видно, на чём основан вывод.
4. Без патчей кода: наблюдения + гипотеза причины + как воспроизвести.

Свой эталон сохрани и машиночитаемо — `_audit/<file_id>/auditor_reference.txt`, строка
`sheet|page|key|N|N-1` (key = код CVM или название; «-» = прочерк, пусто = не напечатано); для
4-колоночного документа можно с колонками Controladora:
`sheet|page|row|label|Conso N|Conso N-1|Contr N|Contr N-1` (Cibra 2026-11-05). По нему сессия исправлений
и повторный аудит сверяют результат своим сравнителем (`_temp/fix/cmp.py` и его копии).

## 6. Сравнение с моделью reciTAL 6051 — если пользователь просит

**Контекст.** Агент 6051 `Brazil_OCR202606_V4 copy reciTAL` — копия нашего агента 5485, в которой
reciTAL изменила одну настройку: в группе `ONLY_AMOUNT` метка `AMOUNT_N-1` тоже сделана primary
(каждое число извлекается отдельной subgroup). Цель — чтобы извлечение перестало терять числа таблиц.
Вопрос пользователя: что лучше для прода и насколько корректен наш постпроцессинг на каждой модели.

**Состояние на 2026-11-05.** По аудиту Cibra 12.2024 (`_audit/AUDIT_REPORT_2026-11-05.md`) пользователь
выбрал для прода конфигурацию 6051; пайплайн берёт период и тип колонки из шапки таблицы (зоны, `CLAUDE.md`
#31). Не измерено: поведение 6051 там, где зон нет (2 колонки, ITR, SERASA, ВСЕ ЗАГЛАВНЫЕ) — следующее
сравнение моделей стоит делать на документах этих типов.

**Пары.** Пользователь загружает один и тот же PDF в оба агента. Найди id в каждом по имени файла
(`files 5485`, `files 6051`); оба id прогони через `audit_run.py`. Четыре варианта:

| Вариант | Извлечение | Слой words |
|---|---|---|
| **A** | агент 5485 | нет (как в проде сегодня) |
| **B** | агент 5485 | да |
| **C** | агент 6051 | нет |
| **D** | агент 6051 | да |

**Что сравнить — по каждому числу эталона:** есть ли оно в извлечении и верна ли там метка года;
куда его поставил постпроцессинг (строка, год, колонка Contr/Conso, значение); что видно в Excel;
SBS-метки и `sbs_fields`. Исход ячейки: ✓ / нет / не та строка / не тот год / не та колонка /
неверное значение / лишнее (числа нет на странице). Числа сравнивай по значению + строке, не по
координатам (у разных загрузок они немного отличаются).

**Метрики по A–D:** полнота извлечения; полнота выхода; доля правильно размещённых чисел;
**«тихие» ошибки** (не тот год / колонка / строка / значение — самое важное: пропуск видно, тихую
ошибку нет); сколько ошибок провайдера постпроцессинг исправил и сколько внёс своих.

**В отчёте** (раздел «Сравнение моделей»): таблица метрик A–D; таблица расхождений с эталоном
(`строка · колонка · на странице · A · B · C · D`) и число совпавших ячеек; вывод — какой вариант
лучше для прода, при каких условиях, что нужно изменить у reciTAL и что у нас (словами, без правок кода).
